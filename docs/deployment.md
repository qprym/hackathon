# Развёртывание и сопровождение

Состояние на 26.10.2026: приложение подготовлено и проверено локально. Внешнего сервера/домена нет; внешний HTTPS не проверен. Целевая локальная LLM ещё не установлена. Ресурсы модели нужно планировать отдельно от контейнеров приложения.

## Существующий preview

```powershell
.\scripts\start-preview.ps1
```

[127.0.0.1:8081](http://127.0.0.1:8081/) — demo / demo-alfa-2026. Проект `alfa-context-preview` использует `compose.yaml`, `compose.verify.yaml`, `compose.preview.yaml`, сохраняет свои тома и не меняет основной `alfa-context` на 8080. Остановка: `scripts/start-preview.ps1 -Stop`.

Это локальный снимок данных кейса и исторических ответов. В нём пустые ключ и URL удалённого провайдера, `DEMO_MODE=true`, `PREVIEW_CACHED_ONLY=true`, замороженный RSS. Неизвестный реальный разбор возвращает явное отсутствие результата; учебный ответ его не заменяет. Сохранённая история: 117 запросов / 93,14307 ₽ учтено, включая прежние резервы. Новых платных запросов нет. Новый том начинает только с синтетических данных.

## Чистая приёмка

Администратор может подключить модель через «Настройки LLM» даже на preview. Сохранённые настройки имеют приоритет над исходным окружением и сохраняются при перезапуске; скрипт preview их не удаляет. По умолчанию новый том не содержит подключения. Само сохранение формы не проверяет доступность модели и не расходует токены.

Освободить 8081, остановив preview. Из корня выполнить `scripts/verify-local.ps1`. Скрипт создаёт отдельный `alfa-context-check-YYYYMMDDhhmmss`, собирает контейнеры и проверяет:

1. Миграции на новой PostgreSQL и `alembic check`.
2. Отсутствие ключа, URL и возможности платных обращений.
3. Playwright: полный учебный путь, права viewer, новая статья/источник/отзыв/вопрос, локальная разметка.
4. Очередь после перезапуска API и последующего запуска worker.
5. Дамп PostgreSQL, восстановление в отдельную БД и сравнение числа/содержимого строк всех таблиц; бинарный round-trip файла источника.

Обычный запуск удаляет только контейнеры своего проекта, сохраняя тома. `-KeepRunning` оставляет его для просмотра. Имя проекта выводится в конце. После проверки вернуть preview. Проверка резервной копии выполнена на чистом учебном наборе; это не замер времени восстановления полного массива кейса.

## Будущий сервер

Нужны Linux, Docker Compose 2.24.4+, домен с A/AAAA и открытые 80/443. Caddy обслуживает HTTPS. БД и API не публикуются напрямую. Для локальной LLM нужен уже поднятый совместимый сервер в разрешённой локальной сети; аппаратные требования определяются выбранными весами, контекстом и нагрузкой.

1. Перенести код проверенного тега; подготовить `.env` из шаблона. Секреты и `data/private` не включать в образы/Git.
2. До первого создания БД установить сильные DEMO_PASSWORD и POSTGRES_PASSWORD, согласовать пароль в DATABASE_URL. Изменение DEMO_PASSWORD позже не меняет существующие пароли.
3. Задать DOMAIN, COOKIE_SECURE=true, ALLOWED_ORIGINS=https://<домен>.
4. Сначала выполнить проверку в учебном режиме:

```sh
docker compose -f compose.yaml -f compose.production.yaml up --build -d --wait
```

5. Проверить health, вход/выход, secure cookie, права viewer, источники, вопрос и отзыв через внешний HTTPS; закрытость портов БД/API проверяется снаружи.
6. После подготовки локальной модели заполнить «Настройки LLM» в кабинете администратора: локальный режим, URL, ID/ревизию и необязательный токен. Включить вызовы и отдельный флажок автоматической обработки активных профилей. Альтернатива — `compose.local-llm.yaml` вместе с production overlay; его настройки окружения действуют после сброса настроек формы. Начать с одного профиля, измерить время/память/очередь, затем расширить. Денежной квоты локальный режим не имеет.
7. Перенести разрешённые материалы кейса защищённым способом, импортировать и проверить права. Доступ жюри выдаётся отдельно по решению владельца; сейчас он не выдан.

## Резервные копии и откат

Подключение и ключ из интерфейса находятся отдельно от БД и исходных документов: том `runtime_settings`, файл `/app/runtime/llm.json`. API и worker используют один файл; запись атомарная, права в Linux — `0600`, каталог — `0700`. Это секретный конфигурационный файл, а не зашифрованное хранилище. Он не включён в обычный дамп PostgreSQL и демонстрационные фикстуры. Копировать его только защищённым способом либо повторно задать подключение через интерфейс после восстановления; не публиковать том/файл вместе с примерами.

Хранить совместимые версии БД и `source_files`; одного SQL недостаточно для исходных PDF. Для PostgreSQL безопасен бинарный dump внутри контейнера с последующим `docker compose cp` (не двоичное перенаправление PowerShell):

```sh
docker compose exec -T db pg_dump -U alfa -d alfa -Fc -f /tmp/alfa.dump
docker compose cp db:/tmp/alfa.dump ./alfa.dump
docker compose exec -T api tar -czf /tmp/sources.tar.gz -C /app/uploads .
docker compose cp api:/tmp/sources.tar.gz ./sources.tar.gz
```

Перед переносом приостановить записи импорта/анализа, чтобы снимки БД и файлов соответствовали друг другу; копии хранить вне публичного репозитория с контролем доступа. Проверять восстановление сначала в отдельной БД/томе. `scripts/verify_backup.py` автоматизирует такой контроль только для изолированного проверочного проекта и отказывается работать с основной БД. Для отката нужны прежний тег и совместимая резервная копия, а не изменение опубликованных миграций.

Мониторить health, ошибки источников, длину/возраст очередей, insufficient/failed, отзывы и задержки модели. После смены весов менять LLM_MODEL_REVISION и повторять контрольный набор. Полный fingerprint корпуса и попарные модельные сравнения подходят для прототипа; предел масштаба и GPU-конкурентность должны быть измерены перед расширением.
