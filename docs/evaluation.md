# Оценка качества

Цели: Precision@5 ≥ 0,8; минимум 95% проверенных фактических утверждений подтверждаются указанными фрагментами; все ключевые выводы имеют основания или маркировку предположения.

Нельзя считать эти цели достигнутыми по успешным unit-тестам, совпадению ID источников или синтетической демоленте. Проверка содержания требует независимой оценки.

## Набор

`data/evaluation/events.json` содержит 50 **синтетических** событий: 30 development и 20 holdout. Это заготовка процесса проверки, не независимый рыночный benchmark. Метки намеренно оставлены `null`, чтобы не выдавать правила самого ранжировщика за экспертную разметку. Перед итоговой оценкой заменить/дополнить набор реальными публикациями из разрешенных источников. Все сообщения об одном событии должны находиться только в одном split; новости holdout нельзя использовать при настройке.

Эксперт оценивает каждое событие для 3 компаний × 3 ролей по шкале 0 — нерелевантно, 1 — полезный контекст, 2 — непосредственно важно. Релевантным для Precision@5 считается 1 или 2. Размечать по доступным признакам, без знания ответа модели. Сохранить автора/дату разметки и объяснения спорных случаев. Для публикации цифр нужны утвержденные метки всех участников сравнения.

`scripts/evaluate.py` рассчитывает Precision@5 для указанного split по этой разметке. Если метки не заполнены, программа сообщает о неполной оценке и не выдает показатель успеха. `scripts/build_eval_fixture.py` создает начальную заготовку и отказывается перезаписывать уже существующий файл, сохраняя ручную разметку.

## Подтвержденность

На holdout собрать результаты реальной модели. Для каждого утверждения эксперт открывает приведенный фрагмент и ставит: подтверждено / противоречит / недостаточно данных / условный сценарий. Фактическая подтвержденность = подтвержденные фактические утверждения / все фактические утверждения. Отдельно считать неподтвержденные утверждения от имени банка, персонализацию, полезность действий и долю корректных отказов.

Сравнить базовые правила и live-режим на одинаковом корпусе. Проверить удаление банковской аналитики, изменение клиентского признака, противоречивый источник, старую дату, нераспознанный PDF и вредоносную инструкцию в новости. Следить за временем, расходом и количеством повторных поисков.

В интерфейсе сохраняются обратная связь, число запусков, задержки, расходы и ошибки источников. Еженедельную экспертную оценку, если проект продолжится, проводят на новых событиях и жалобах пользователей; автоматическое расписание этой проверки не создано.

## Реальный набор и воспроизводимые команды

22.10.2026 создан локальный `data/private/evaluation.json`: 30 development и 20 holdout реальных событий для U_26491, U_989, U_6923 × трёх ролей. Это заготовка независимой разметки, а не уже пройденная проверка. В holdout оставлены 180 пустых меток. Честный результат оценщика — `incomplete`. После изменений алгоритма нужен новый неиспользованный holdout.

```powershell
docker compose run --rm --no-deps -v "${PWD}:/workspace" api python /workspace/scripts/export_evaluation.py --companies U_26491 U_989 U_6923 --output /workspace/data/private/evaluation.json
docker compose run --rm --no-deps -v "${PWD}:/workspace" api python /workspace/scripts/evaluate.py --data /workspace/data/private/evaluation.json --split holdout
```

Экспорт также создаёт `.claims.json` с утверждениями завершённых live-разборов и их основаниями. При отсутствии реальных вызовов он пуст. Эксперт заполняет `supported`, `reviewer`, комментарий. `scripts/evaluate_claims.py` считает подтверждённость только при полной разметке фактических утверждений; иначе возвращает `incomplete`. Экспорт и расчёт метрик не обращаются к LLM. При лимите всего 20 вызовов сначала проверяется один короткий live-разбор; полная оценка качества может потребовать отдельного согласованного бюджета.
